Open dependencies, unresolved decisions, and known risks. Check this before assuming an account, integration, or decision is already in place — it keeps [PLANS.md](./PLANS.md) from silently drifting on unstated assumptions.

## How to use this document

- When an item is resolved, move it to the bottom of its section under a `### Resolved` subheading with the date and outcome — don't delete it, so we keep a decision trail.
- If a phase-gate item in PLANS.md can't be completed because of something listed here, leave the checkbox unchecked and reference the item ID (e.g. `DEP-3`) in the checkbox's context.

### WhatsApp Business API Ingestion — Requirements (researched 2026-08-15, per explicit request, informational only — nothing built)

Requested directly parallel to the completed Instagram build (`DEP-4`), to answer "what's needed to set up WhatsApp ingestion via API as we have for Instagram." Verified against live 2026 sources (WebSearch + the current Meta for Developers docs), not stale training data — this session already found Meta's Instagram API surface disagreeing with its own docs once, so freshness was checked deliberately rather than assumed.

**The genuinely reusable part.** Webhook infrastructure is close to identical to what's already built and proven for Instagram: same `X-Hub-Signature-256` HMAC-SHA256 verification pattern, same GET handshake (`hub.mode`/`hub.verify_token`/`hub.challenge`) to register the callback URL, same "return 200 within 5 seconds, no polling, process async" delivery model. `web/src/app/api/channels/instagram/webhook/route.ts`'s shape (signature check → `after()`-wrapped background processing → idempotent `external_message_id` handling) should port to a WhatsApp route with mostly config changes, not a rewrite. `token-crypto.ts` (AES-256-GCM at-rest encryption for channel credentials) and the `channel_connections` zero-RLS-policy pattern apply unchanged.

**What's genuinely new and harder than Instagram, in onboarding order:**
1. **Meta Business Portfolio + real business verification** — not just a Developer App. Confirming legal business name, address, and registration documents against Meta's own review, typically 2–4 business days, separate from and prior to any app-level work. Instagram Login never required this; WhatsApp does.
2. **A WhatsApp Business Account (WABA)** provisioned under the verified Business Portfolio, plus at least one phone number added to it and ownership-verified through WhatsApp Manager (a *different* console from the developer App Dashboard) before any API registration call can succeed.
3. **Phone number registration is API-only** — cannot be done through WhatsApp Manager or the App Dashboard UI, only a `POST` with a self-chosen 6-digit two-step-verification PIN. Rate-limited to 10 registration attempts per number per rolling 72 hours (error `133016` beyond that) — worth building this carefully the first time rather than iterating live against it.
4. **`DEP-2` (direct Cloud API vs. a BSP like Twilio/360dialog/Gupshup) has to actually be decided before building**, unlike Instagram where there was only one path. Direct Cloud API is what the webhook/send code above assumes and avoids a middleman markup (BSPs typically add $0.003–$0.010/message on top of Meta's own per-message rate), but a BSP can shortcut business verification and phone provisioning through their own onboarding flow — worth deciding once a real pilot business's timeline pressure is known, not before.
5. **`DEP-3` (template pre-approval) is a hard, unavoidable constraint for the send side**, not just a nice-to-have — unlike Instagram, which has no equivalent 24-hour-window/template system. Inside a live 24-hour customer-service window (i.e., replying to a message the customer *just* sent — Engage's core live-reply case), sends are free-form and free, the same as Instagram. Outside that window — any Recover follow-up to a dormant lead, any Prevent-style re-engagement nudge after a quiet gap — the message must be a pre-approved template, submitted to Meta ahead of time (approval usually minutes to a few hours, up to 48h for complex marketing copy). This directly affects Recover's `draft-message.ts` output: a real WhatsApp Recover send can't just be free AI-drafted prose the way an Instagram or in-window WhatsApp reply can; it needs to either fit a pre-approved template's variable slots or get a new template approved per message shape.
6. **Pricing model is mid-change, and the date matters**: Meta moved from conversation-based to per-message pricing on 2025-07-01 (now the current model — billed per delivered template message, category × recipient-country, categories being marketing/utility/authentication/service). **A second change is already scheduled for 2026-10-01** — about six weeks from today (2026-08-15) — after which the currently-free in-window service messages and in-window utility templates also become billed per message; Meta is committed to publishing the exact new rates by 2026-09-01. Worth checking those published rates before finalizing Engage/Recover WhatsApp unit economics rather than budgeting off the current free-service-message assumption, since it's set to stop being free.

**Net comparison to Instagram**: Instagram (`DEP-4`) was one Meta Developer App, one OAuth-style connect, no per-message billing, no business verification gate, no template system — genuinely the easier of the two channels, which is consistent with why it shipped first. WhatsApp adds a real, multi-day business-verification prerequisite, a second console (WhatsApp Manager) alongside the Developer App Dashboard, a hard template-approval requirement for the Recover/Prevent-follow-up use cases specifically (not the live-reply case), and per-message costs that are about to expand to a channel that's currently free. None of this blocks starting — `DEP-1` (Business verification + WABA) is the actual first blocking step, same shape as `DEP-4` was for Instagram before this session started it.

**`DEP-1` cleared 2026-08-23** — founder completed business verification and provisioned a WABA. **Zernio evaluated the same day** as a third `DEP-2` option (founder asked directly: "read zernio.com documentation and see how if at all it can be useful to capture"). Zernio is a unified messaging/publishing API + MCP server across 16 platforms including WhatsApp; its docs are explicit that it doesn't broker WABA access — the same business verification and WABA provisioning above is required regardless of which `DEP-2` path is chosen. Where it would have helped: template management, the 24h-window rule, and media limits are handled by its API, and its webhook model (HMAC-SHA256 `X-Zernio-Signature`, `message.received` events, idempotency via event ID) is close enough to what's already proven for Instagram/Paystack that integration friction would have been low. Against it: a per-connected-account fee, and real customer messages routing through a third-party vendor — a trust consideration for a product built on handling customer conversations carefully. **Founder decided direct Meta Cloud API** — reuses the exact webhook/signature/token-encryption patterns already proven for Instagram, no added third-party dependency.

**Still needed before real ingestion can be built/tested** (only `WHATSAPP_BUSINESS_ACCOUNT_ID` is in `.env.local` so far, confirmed via direct file check): a phone number added to the WABA in WhatsApp Manager (manual, founder-only step — generates a `phone_number_id`), that number registered via the Cloud API's register endpoint (a self-chosen 6-digit 2FA PIN, rate-limited to 10 attempts/72h so worth getting right the first time), a permanent system-user access token scoped to `whatsapp_business_messaging`, and a Meta Developer App with the WhatsApp product added (app secret + webhook verify token, same shape as `INSTAGRAM_APP_ID`/`INSTAGRAM_APP_SECRET`/`INSTAGRAM_WEBHOOK_VERIFY_TOKEN`).
