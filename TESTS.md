# CAPTURE — Test Log

Actual test results go here, most recent entry first within each table. This log is what makes checkboxes in [PLANS.md](./PLANS.md) legitimate — do not check a phase-gate box there without a corresponding row here.

## How to use this document

- Log a row **every time** a phase-gate test (or regression re-run) is executed, whether it passes or fails.
- Never delete a failing result — leave it, add a new row when it's fixed, so the history shows the fix actually happened.
- "Type" values: `unit`, `integration`, `e2e`, `security`.
- Link related PLANS.md checkbox and/or OUTSTANDINGS.md item where relevant in Notes.

## Large-Batch Upload Cap and Classification Resilience (DEV-7)

Raising the cap alone would also have made classification's fully-sequential loop — already at risk of exceeding Vercel's ~300s function budget for a large batch, and with no isolation between conversations since `classifyConversation()` re-throws any non-`NoObjectGeneratedError` failure — a much bigger latent risk. ## Engage Direction — Live Webhook Message Processing (Phase 5.2)

The piece that makes Engage actually real-time rather than a historical-only audit: the webhook's POST handler now parses real inbound message events, resolves the owning business/customer/conversation, runs them through the same tested `handleInboundMessage()` engine, and — new — actually sends the AI's reply back to the real customer via Instagram's Send API when the engine produces one. Chose to wire this next (over response-time metrics) because there's no meaningful "after Engage" data to measure until Engage is actually operating live — reasoning stated directly to the founder before starting, not just decided silently.

**Safety-relevant additions found necessary while building this, not planned in advance:**
- A real, previously-latent gap in `handleInboundMessage()`: the engine's `response` field is nullable by schema (`can_answer_from_knowledge` can legitimately be paired with `response: null`), and the existing escalate/respond branch only checked `result.escalate`, not whether `response` was actually present. Harmless before (nothing ever sent the null body anywhere), but the live send path would have attempted to POST `null` as message text to a real customer. Fixed by folding `!result.response` into the escalation condition — a model producing a malformed escalate=false/response=null result now safely escalates instead, per addendum §7 ("safe incompleteness over confident wrongness").
- Meta's webhook delivery is documented at-least-once, not exactly-once — redelivery of the same event must not trigger a second AI reply. Fixed via `handleInboundMessage`'s new optional `externalMessageId` param (stored on the inbound message row) plus an explicit pre-check in the webhook route before any processing starts.
- Background processing via a bare `.catch()`'d promise (no `after()`) would risk the serverless function terminating before it finished — caught and fixed during this same build pass, not after a real failure.

## Phase 5.1 — Four-Tier Answerability + Safe-Response Gate

Addendum §9–§11's four-tier answerability classification (A safe / B safe-with-constraint / C human-required / D unknown), replacing the original binary `can_answer_from_knowledge` gate. `web/src/lib/prevent/schema.ts`'s `engineResponseSchema` now carries an `answerability: "A"|"B"|"C"|"D"` enum instead; `engine.ts`'s system prompt rewritten to teach the model the four-tier framework directly (each tier's definition and examples lifted near-verbatim from the addendum). New file `web/src/lib/prevent/safe-response-gate.ts` exports `evaluateSafeResponseGate()` — the single, named, auditable function formalizing §11's five conditions (intent understood / business info exists / groundable / no escalation rule triggered / no sensitive-exception condition), replacing logic that was previously split between `engine.ts`'s ad hoc defense-in-depth check and `process.ts`'s `!result.escalate && result.response` condition. Both call sites now share this one function; its safe branch returns the validated response string itself, not just a boolean, so `process.ts` can never reach a "safe but null response" state at the type level (verified via `tsc --noEmit`, not just review).

No DB schema change — the tier is a structured-output field, not persisted to a new column; this keeps the change scoped to classification granularity and gate logic, per V1 scope guardrails (§30), not a speculative new dashboard feature nobody asked for.

**A genuinely new safety property this pass caught nothing on, but is worth recording**: `SENSITIVE_INTENTS` (`complaint`, `human_assistance`) in the gate forces escalation regardless of what tier the model assigns — a defense against exactly the "don't rely solely on model confidence" failure mode the addendum warns about (a model mislabeling a complaint as tier A/B). ## Conversation Ordering — `last_message_at` Maintenance Fix

Founder-caught 2026-08-20: "I would expect the most recent messages showing first" on the Engage dashboard. ## `/ultrareview` Findings (Cloud Review) — Two Real Bugs Fixed, One Process Gap Surfaced

`/ultrareview` run against `main`, 2026-08-21. Three findings reported; investigated all three against the actual working tree before acting on any (per this project's standing discipline — verify, don't take agent findings on faith).

**bug_006 — escalation email fires on every re-escalation (CONFIRMED, fixed)**: a conversation already sitting in `human_required` (escalated, not yet taken) isn't "human active" by `isHumanActive()`'s check — correctly so, since the AI needs to keep processing further messages in case a human does take over. But that meant every subsequent message on an already-escalated conversation re-ran the full escalation branch: a chatty customer sending 5-10 messages before anyone responded produced 5-10 identical alert emails, each stomping the original `escalated_at` (breaking "escalated N minutes ago"/SLA ordering) and the original `escalation_reason` with whatever the latest message produced. On a re-escalation, state is restored to `human_required` (so the conversation doesn't get stranded in `ai_handling`) but `escalated_at`/`escalation_reason` are left untouched and the notification is skipped entirely — the caller still gets the current message's own reason back (useful for the Simulate form's live feedback), but nothing is persisted or re-sent.
